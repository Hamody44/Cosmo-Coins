# البوت الثاني: `$say` و`$ping` و`$numbers`

هذا بوت Discord مستقل بلغة Python باستخدام `discord.py-self`، ولا يمرر إعداد `Intents`. يوجد بالكامل داخل `second_bot/` ويعمل بتوكن حساب المستخدم. يستخدم وضع account-client الذي يسمح له بمعالجة أوامر يرسلها حساب آخر؛ أما `self_bot=True` في المكتبة فيعني تجاهل رسائل الحسابات الأخرى، لذلك لا يُستخدم هنا. عند كتابة `$say hi` ينتظر ثانية واحدة، ثم يحذف رسالة الأمر ويرسل `hi`. يسمح باستخدامه لمالك الحساب أو لأي عضو يحمل الرتبة المحددة في `SAY_ALLOWED_ROLE_ID`. يعرض الأمر `$ping` حالة الاتصال وزمن استجابة Discord بالميلي ثانية بعد تأخير ثانية واحدة. يتيح `$numbers` أو `$استخراج_الأرقام` إرفاق صورة لاستخراج الأرقام الظاهرة فيها؛ يستخدم OCR.Space للنوع الأول وOCR المحلي للنوع الثاني، مع حد 8 ميغابايت. يتيح أيضًا `$start` و`$restart` و`$shutdown` و`$status` للتحكم في البوت الأساسي فقط. لا يستخدم هذا البوت أوامر السلاش؛ فهو يعالج أوامر البادئة فقط. يقبل البوت الأوامر فقط في السيرفرات التي يوجد فيها بوت Cosmo-Coins الأساسي أيضًا؛ ينشر البوت الأساسي قائمة سيرفراته محليًا كل 30 ثانية، ويتجاهل البوت الثاني الأوامر إذا غابت القائمة أو تجاوز عمرها 90 ثانية.

## الإعداد

1. جهّز الحساب الذي سيعمل به self-bot وفق إعداداتك، ثم استخدم توكن الحساب المخصص له.
2. انسخ `second_bot/.env.example` إلى `second_bot/.env`، ثم أدخل `SECOND_BOT_TOKEN` و`SAY_ALLOWED_ROLE_ID` و`OCR_SPACE_API_KEY`. يمكن إضافة `GEMINI_API_KEY` أو `OPENROUTER_API_KEY` لتفعيل المزود الاحتياطي إذا فشل OCR.Space في قراءة النوع الأول. ويمكن إضافة `VERYFI_CLIENT_ID` و`VERYFI_USERNAME` و`VERYFI_API_KEY` لتفعيل Veryfi عند تعارض نتائج OCR.Space؛ يرسل البوت نسخة محسنة واحدة فقط إلى Veryfi. يحدد `VERYFI_MONTHLY_REQUEST_BUDGET` السقف المحلي الشهري، وقيمته الافتراضية 80 طلبًا، ويحفظ العداد في `second_bot/.runtime/veryfi_rate_state.json`. النوع الثاني لا يحتاج أي مفتاح API. لا يقبل البوت الثاني `DISCORD_BOT_TOKEN` كبديل، لتفادي استعمال توكن البوت الأساسي عند غياب إعداد توكن منفصل. قيمة الرتبة هي **Role ID** من السيرفر، وليست اسمها. فعّل Developer Mode في Discord ثم اختر Copy ID. لا تشارك التوكن أو مفاتيح API ولا تضعها في Git.
3. لا يحتاج البوت الثاني إلى إعداد `Gateway Intents` في هذا الوضع. يظل البوت الأساسي منفصلًا ويستخدم `Intents` الخاصة به.
4. جهّز وصول البوت الثاني إلى السيرفرات المطلوبة وفق إعدادات Discord الحالية، مع الصلاحيات المذكورة أدناه.

## الصلاحيات المطلوبة

- **View Channels** و**Send Messages** في القنوات التي سيعمل فيها.
- **Manage Messages** حتى يتمكن من حذف رسالة الأمر التي كتبها المستخدم.
- في سلاسل النقاش (Threads)، امنحه أيضًا **Send Messages in Threads**.
- لا يحتاج البوت إلى صلاحية `Administrator`. إذا لم تتوفر صلاحية الإرسال، فسيسجّل ذلك في الطرفية لأن Discord لن يسمح له بإرسال رسالة خطأ داخل القناة.
- يقبل `SECOND_BOT_TOKEN` توكن الحساب الذي سيعمل به self-bot، ويمكن إدخاله خامًا أو مع بادئة `Bot ` اختيارية عند استخدام توكن بوت متوافق.

يستخدم البوت `discord.AllowedMentions.none()` لكل ما يرسله، لذلك لا يؤدي النص إلى تنبيه أشخاص أو أدوار أو `@everyone`.

## تثبيت التبعيات

تُثبّت كل مجموعة متطلبات في بيئة افتراضية مستقلة لتجنب تعارض تبعيات البوتين. سكربت `run_bots.sh` ينشئ البيئات الافتراضية ويثبت أو يحدّث المكتبات تلقائيًا عندما يتغير ملف المتطلبات الخاص بكل بوت، لذلك لا تحتاج إلى تعديل السكربت عند إضافة مكتبة جديدة. ملفات المتطلبات تحمل امتداد `.lock` حتى لا تلتقطها لوحات الاستضافة وتثبتها في Python العام. للتثبيت اليدوي من جذر المستودع:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r cosmo_requirements.lock

python3 -m venv second_bot/.venv
second_bot/.venv/bin/python -m pip install --upgrade pip
second_bot/.venv/bin/python -m pip install -r second_bot/cosmo_second_requirements.lock
```

يعمل OCR المحلي باستخدام Pillow فقط، ولا يعتمد البوت على OpenCV أو NumPy. هذا يجعله مناسبًا للاستضافات محدودة المساحة، ويستخدم `models/local_ocr_model.json` المتوافق مع Pillow مباشرةً.

قبل التشغيل، أنشئ أيضًا ملف `.env` الخاص ببوت Cosmo-Coins في جذر المستودع وفق إعداداته الحالية، إن لم يكن موجودًا بالفعل. لا تستبدل ملف `.env` قائمًا.

## تشغيل البوتين معًا

من جذر المستودع:

```bash
chmod +x run_bots.sh
./run_bots.sh
```

يشغّل السكربت `main.py` الخاص بـ Cosmo-Coins من جذر المستودع، ثم يشغّل `second_bot/main.py` من مجلد `second_bot/`؛ وبذلك يقرأ كل بوت ملف `.env` الخاص بمجلده وبيئته الافتراضية. إذا لم توجد بيئة افتراضية لأحدهما، يستخدم السكربت `python3` المتاح. أوقف البوتين معًا باستخدام `Ctrl+C`.

يمكن تشغيل البوت الثاني وحده للاختبار:

```bash
cd second_bot
.venv/bin/python main.py
```

إذا كانت الاستضافة تسمح بتشغيل ملفات Python فقط، اجعل ملف التشغيل هو `run_bots.py` الموجود في جذر المستودع. هذا الملف يشغّل `run_bots.sh` تلقائيًا من المسار الصحيح، مع إبقاء بيئة كل بوت منفصلة:

```bash
python3 run_bots.py
```

## سلوك الأمر والأخطاء

- أوامر التحكم متبادلة وليست ذاتية: البوت الأساسي يستقبل `!start` و`!restart` و`!shutdown` و`!status` للتحكم في `second_bot`، والبوت الثاني يستقبل `$start` و`$restart` و`$shutdown` و`$status` للتحكم في البوت الأساسي. الأوامر محمية بمالك البوت، ويسمح البوت الثاني أيضًا بالحساب الحالي أو الرتبة الموجودة في `SAY_ALLOWED_ROLE_ID`.
- يحتفظ `run_bots.sh` بملف PID مستقل لكل بوت وملف طلبات مشترك. لذلك لا يؤدي `shutdown` لأحدهما إلى إيقاف الآخر، ولا يشغّل `start` نسخة ثانية إذا كان البوت يعمل. أمر `restart` يوقف العملية ثم يعيد تشغيل `main.py` الحالي باستخدام البيئة الافتراضية نفسها.
- بعد تنفيذ `!shutdown` استخدم `$status` من البوت الثاني للتحقق من حالة البوت الأساسي، وبعد تنفيذ `$shutdown` استخدم `!status` من البوت الأساسي للتحقق من حالة البوت الثاني. ستظهر الحالة `running (PID ...)` أو `stopped`. ويمكن كذلك فحصها من Console عبر `bash run_bots.sh control status primary` أو `bash run_bots.sh control status second_bot`.
- `$say hi` ينتظر ثانية واحدة، ثم يحذف رسالة الأمر ويرسل `hi` دون تفعيل المنشنات.
- `$ping` ينتظر ثانية واحدة ثم يعرض أن البوت متصل وزمن استجابة Gateway الحالي بالميلي ثانية.
- `$numbers` يحتاج إلى صورة مرفقة مع الرسالة، ثم يحدد نوعها محليًا. يرسل النوع الأول إلى OCR.Space Engine 3 عبر أربع نسخ: الأصلية، نسخة محسنة التباين، ونسختين مكبرتين ثلاث مرات إحداهما بعتبة Otsu العالمية والأخرى بعتبة محلية تكيفية باستخدام خلفية Gaussian محلية. يعرض نتيجة كل معالجة بالتفصيل كما هي، ويستخدم الإجماع داخليًا للتحقق من موثوقية القراءة؛ ولا يستدعي Engine 2. عند تعارض النتائج يجرب Veryfi عبر نسخة محسنة واحدة عند إعداد مفاتيحه، ثم Gemini وOpenRouter عند توفر المفاتيح بدل قبول أول قراءة مختلفة. نموذج Gemini الاحتياطي الافتراضي هو `gemini-3.5-flash-lite`؛ ويحوّل البوت تلقائيًا قيمة `gemini-2.5-flash-lite` القديمة إلى هذا النموذج. أما النوع الثاني فيستخدم نموذج Pillow المحلي دون أي طلب خارجي. الصور المدعومة هي JPEG وPNG وWebP وGIF، والحد الأقصى 8 ميغابايت.
- `$testall` (للمالك أو الرتبة المصرح بها فقط) يقرأ الصور المعلّمة من `captcha_samples/label.csv`، ويرسل كل صورة من `type1` إلى Engine 3 بالمعالجات الأربع، ثم يرسل ملخص الدقة وملف `testall_engine3_report.csv`. يبيّن التقرير النتائج لكل معالجة، عدد الصور المطابقة تمامًا، حالات الخطأ برقم أو رقمين أو ثلاثة أو أربعة/خمسة، الصور غير المقروءة، وفشل الخدمة منفصلًا، إضافة إلى مواضع الأرقام التي التبس فيها التعرف. يحفظ البوت checkpoint في `second_bot/.runtime/testall_engine3_checkpoint.json` بعد كل معالجة مكتملة، ويستأنف من أول معالجة غير مكتملة بعد التوقف أو 429 دون إعادة الطلبات السابقة. عند اكتمال الاختبار وإرسال التقرير يحذف checkpoint؛ لذلك يبدأ التشغيل التالي من أول صورة. إذا تغيرت الصور أو التسميات أو نسخة المعالجة يبدأ اختبارًا جديدًا بدل استخدام نتائج قديمة. قد يستهلك اختبار 100 صورة حتى 400 طلب (السقف اليومي المحلي الافتراضي)؛ لا تترك مساحة لاستخدامات OCR أخرى في اليوم نفسه، وسيستأنف الاختبار من checkpoint بعد تجدد الحد إذا توقف.
- يطبق هذا البوت الثاني cooldown شخصيًا مدته 30 ثانية لكل مستخدم وفي كل سيرفر. بوت Cosmo الأساسي لا يطبق cooldown.
- يرفع البوت النوع الأول إلى OCR.Space عبر طلب multipart، باستخدام `scale=true` و`detectOrientation=true`، مع مهلة 20 ثانية لكل محاولة. جميع أوامر البوت تمر عبر محدد مشترك يضع افتراضيًا ثانيتين بين الطلبات، يحترم `Retry-After` عند توفره، ويطبق سقفًا محليًا محافظًا قدره 400 طلب في يوم UTC مع مهلة ساعة بعد 429 إذا لم يحدد المزود مدة انتظار. تحفظ حالة المعدّل في `second_bot/.runtime/ocr_space_rate_state.json` لتبقى بعد إعادة التشغيل. تشترك أوامر `$numbers` و`$testall` في هذا الحد. تحفظ حصة Veryfi الشهرية في `second_bot/.runtime/veryfi_rate_state.json`، ولا يُستدعى إلا عند تعارض OCR.Space. تذكر [وثائق OCR.Space](https://ocr.space/ocrapi) أن الخطة المجانية محدودة بـ500 طلب يوميًا لكل عنوان IP؛ السقف المحلي يترك هامشًا، لكنه لا يحسب استعمال تطبيقات أخرى على عنوان IP نفسه.
- أزيلت مكتبة `ddddocr`؛ يستخدم OCR المحلي Pillow فقط للـgrayscale والـthreshold والـmorphology والـresize، مع اعتماد HOG خفيف للتعرف. يوجد نموذج محلي في `models/local_ocr_model.json`، وكود التدريب والتقييم في `train_local_ocr.py` و`local_ocr.py`. يفحص أمر `$numbers` نمط الصورة محليًا؛ إذا اكتشف `type2` وأعاد خمسة أرقام صحيحة يستخدم النتيجة المحلية مباشرةً. أما `type1` فيرفعه إلى OCR.Space عبر `OCR_SPACE_API_KEY`، ولا يُرسل النوع الثاني إلى OCR.Space. على عينة التدريب الحالية (50 صورة `type1` و20 صورة `type2`) حقق المصنف الخانة-بخانة 100% و20/20 تسلسلاً في النوع الثاني، وحقق `type1` باستخدام Pillow نسبة 24.4% و0/50 تسلسلاً كاملاً.
- تُقبل الأوامر فقط في السيرفرات المشتركة بين البوتين؛ تُرفض أوامر الرسائل الخاصة والسيرفرات غير المشتركة بصمت. عند تعذر قراءة حالة البوت الأساسي أو تقادمها، يتوقف تنفيذ الأوامر حتى تُستعاد الحالة الحديثة.
- يرفض النص الفارغ أو الذي يتجاوز 2000 حرف.
- تُرفض محاولة الاستخدام من شخص ليس مالك البوت ولا يحمل الرتبة المحددة.
- يتطلب حذف أمر العضو `Manage Messages`. عند نقصها تظهر رسالة واضحة ما دام للبوت إذن الإرسال.
- تُعالج أخطاء الأمر وDiscord وتسجّل في الطرفية بدل إيقاف البوت.

## اختبارات الوحدة

الاختبارات مكتوبة باستخدام `unittest` ولا تتصل بـDiscord ولا تحتاج رمز بوت حقيقي. بعد تثبيت متطلبات البوت الثاني، شغّلها من داخله:

```bash
cd second_bot
.venv/bin/python -m unittest discover -s tests -v
```

تغطي اختبارات الإعدادات، صلاحيات `!say`، حذف الرسالة، النص الفارغ وحد 2000 حرف، معالجة أخطاء الأمر، وتعطيل المنشنات ونتيجة `!ping`. كما تتحقق من أن OCR.Space Engine 3 وحده يُستدعى، ومن محدد الطلبات والمهلة بعد 429، وحفظ checkpoint والاستئناف من نفس المعالجة ثم بدء اختبار جديد بعد الاكتمال، دون اتصالات فعلية بـOCR.Space.

## تنظيف الملفات غير المستخدمة

لا يمكن تحديد أن ملف Python غير مستخدم بشكل موثوق من خلال الاسم فقط، خصوصًا لأن `cogs/` تُحمّل ديناميكيًا. لذلك يوجد `cleanup_unused_files.py` في جذر المشروع بوضع معاينة افتراضي، ولا يلمس قواعد البيانات أو ملفات `.env` أو `.runtime` أو النسخ الاحتياطية أو البيئات الافتراضية أو المكتبات المثبتة داخلها.

اعرض المخلفات القابلة للحذف والملفات المصدر التي تبدو غير مرتبطة دون حذف أي شيء:

```bash
python3 cleanup_unused_files.py --include-source
```

بعد مراجعة الناتج، احذف فقط المخلفات المولدة الواضحة مثل `__pycache__` وملفات `.pyc`:

```bash
python3 cleanup_unused_files.py --apply
```

الأداة ترفض حذف ملفات المصدر تلقائيًا؛ يجب مراجعة أي ملف مصدر يدويًا أولًا، لأن التحليل الساكن لا يستطيع اكتشاف كل الاستدعاءات الديناميكية أو الملفات المطلوبة من إعدادات الاستضافة.

يمكن فحص المكتبات المثبتة في Python العام لحساب المستخدم دون حذفها:

```bash
python3 cleanup_unused_files.py --clean-user-site
```

وعند التأكد من وجود `.venv` في جذر المشروع و`second_bot/.venv`، يمكن حذف مكتبات المستخدم فقط باستخدام `--apply --clean-user-site`. لا تلمس الأداة أبدًا مكتبات النظام في `/usr/lib` أو `/usr/local/lib`، لأن حذفها قد يعطل لوحة الاستضافة نفسها.

إذا كانت الحزم القديمة ثُبّتت باستخدام `pip` العام وليس `pip install --user`، استخدم المعاينة التالية من Python العام:

```bash
python3 cleanup_unused_files.py --clean-global-site
```

ولحذف حزم pip العامة التي يعرضها Python الأساسي بعد مراجعة القائمة:

```bash
python3 cleanup_unused_files.py --apply --clean-global-site
```

هذا الخيار لا يعمل من داخل `.venv`، ويتطلب وجود بيئتي المشروع أولًا. وهو يحذف حزم pip فقط عبر `pip uninstall`، وليس ملفات النظام أو Python نفسه. لا تستخدمه إذا كانت لوحة الاستضافة أو خدمة أخرى تعتمد على حزم pip العامة نفسها.

عند تشغيل الملف بدون أي معاملات، يعمل الآن الوضع التلقائي المكافئ لـ `--apply --clean-global-site`؛ أي أنه يحذف حزم pip العامة مباشرة بعد التأكد من وجود البيئتين الافتراضيتين. استخدم `--clean-global-site` وحده إذا أردت المعاينة فقط.
