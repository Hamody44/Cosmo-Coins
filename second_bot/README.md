# البوت الثاني: `$say` و`$ping` و`$numbers` وأوامر إدارة السيرفرات

هذا بوت Discord مستقل بلغة Python باستخدام `discord.py-self`، ولا يمرر إعداد `Intents`. يوجد بالكامل داخل `second_bot/` ويعمل بتوكن حساب المستخدم. يستخدم وضع account-client الذي يسمح له بمعالجة أوامر يرسلها حساب آخر؛ أما `self_bot=True` في المكتبة فيعني تجاهل رسائل الحسابات الأخرى، لذلك لا يُستخدم هنا. عند كتابة `$say hi` ينتظر ثانية واحدة، ثم يحذف رسالة الأمر ويرسل `hi`. يسمح باستخدامه لمالك الحساب أو لأي عضو يحمل الرتبة المحددة في `SAY_ALLOWED_ROLE_ID`. يعرض الأمر `$ping` حالة الاتصال وزمن استجابة Discord بالميلي ثانية بعد تأخير ثانية واحدة. يتيح `$numbers` أو `$استخراج_الأرقام` إرفاق صورة لاستخراج الأرقام الظاهرة فيها؛ يستخدم مسار OCR هجينًا للنوع الأول وOCR المحلي للنوع الثاني، مع حد 8 ميغابايت. يتيح أيضًا `$start` و`$restart` و`$shutdown` و`$status` للتحكم في البوت الأساسي فقط. لا يستخدم هذا البوت أوامر السلاش؛ فهو يعالج أوامر البادئة فقط. يقبل البوت الأوامر فقط في السيرفرات التي يوجد فيها بوت Cosmo-Coins الأساسي أيضًا؛ ينشر البوت الأساسي قائمة سيرفراته محليًا كل 30 ثانية، ويتجاهل البوت الثاني الأوامر إذا غابت القائمة أو تجاوز عمرها 90 ثانية.

## الإعداد

1. جهّز الحساب الذي سيعمل به self-bot وفق إعداداتك، ثم استخدم توكن الحساب المخصص له.
2. انسخ `second_bot/.env.example` إلى `second_bot/.env`، ثم أدخل `SECOND_BOT_TOKEN` و`SAY_ALLOWED_ROLE_ID` و`OCR_SPACE_API_KEY`. أضف `GEMINI_API_KEY` لمسار AI الاحتياطي، ويمكن ضبط `TYPE1_AI_TIMEOUT_SECONDS` (الافتراضي 8 ثوانٍ). يستخدم type1 نموذج القوالب الاختياري `models/type1_local_ocr.json` أو المسار المحدد في `TYPE1_LOCAL_OCR_MODEL`. النوع الثاني لا يحتاج أي مفتاح API. لا يقبل البوت الثاني `DISCORD_BOT_TOKEN` كبديل، لتفادي استعمال توكن البوت الأساسي عند غياب إعداد توكن منفصل. قيمة الرتبة هي **Role ID** من السيرفر، وليست اسمها. فعّل Developer Mode في Discord ثم اختر Copy ID. لا تشارك التوكن أو مفاتيح API ولا تضعها في Git.
3. لا يحتاج البوت الثاني إلى إعداد `Gateway Intents` في هذا الوضع. يظل البوت الأساسي منفصلًا ويستخدم `Intents` الخاصة به.
4. جهّز وصول البوت الثاني إلى السيرفرات المطلوبة وفق إعدادات Discord الحالية، مع الصلاحيات المذكورة أدناه.

## أوامر إدارة السيرفرات

الأوامر التالية مخصصة لمالك حساب البوت الثاني فقط، وتعمل داخل السيرفرات فقط ولا تعمل في الرسائل الخاصة. تستخدم هذه الأوامر بادئة البوت الحالية `$`، ولا تغيّر مسار `$numbers` أو منطق Type1/Type2.

- `$guilds` يعرض جميع السيرفرات التي يوجد فيها البوت الثاني مرتبة حسب الاسم. يعرض اسم السيرفر وGuild ID وعدد الأعضاء والمالك، ويحاول إنشاء رابط دعوة دائم من قناة يملك فيها الحساب صلاحية `Create Invite`. إذا تعذر إنشاء الرابط لسيرفر واحد، يظهر أنه غير متاح ويستمر عرض بقية السيرفرات. تُقسّم القائمة إلى رسائل متعددة عند الحاجة حتى لا تتجاوز حد Discord.
- `$join_guild <invite-link>` يقبل فقط روابط `https://discord.gg/...` أو `https://discord.com/invite/...`. يتحقق أولًا من الدعوة ويعرض اسم السيرفر وGuild ID وعدد الأعضاء التقريبي ووقت الانتهاء إن توفر. إذا كان الحساب موجودًا بالفعل فلا يحاول الانضمام. بخلاف ذلك يطلب تأكيدًا صريحًا (`نعم` أو `yes`) خلال 60 ثانية، ثم يستخدم `accept_invite` المتوافق مع حساب Discord المستخدم في هذا المشروع.
- `$leave_guild <guild-id-or-invite-link>` يخرج الحساب من سيرفر محدد باستخدام Guild ID أو رابط دعوة Discord. عند استخدام رابط دعوة، يقرأ الأمر Guild ID أولًا ثم يتحقق من وجود السيرفر في قائمة الحساب قبل تنفيذ المغادرة.

تتعامل الأوامر مع الدعوات المنتهية أو غير الصالحة، عدم توفر السيرفر، وجود الحساب مسبقًا، أخطاء الصلاحيات وDiscord API و429 ومشكلات الشبكة والمهلة برسائل واضحة مع تسجيل التفاصيل في الطرفية دون إيقاف البوت.

## الصلاحيات المطلوبة

- **View Channels** و**Send Messages** في القنوات التي سيعمل فيها.
- **Manage Messages** حتى يتمكن من حذف رسالة الأمر التي كتبها المستخدم.
- في سلاسل النقاش (Threads)، امنحه أيضًا **Send Messages in Threads**.
- لا يحتاج البوت إلى صلاحية `Administrator`. إذا لم تتوفر صلاحية الإرسال، فسيسجّل ذلك في الطرفية لأن Discord لن يسمح له بإرسال رسالة خطأ داخل القناة.
- يقبل `SECOND_BOT_TOKEN` توكن الحساب الذي سيعمل به self-bot، ويمكن إدخاله خامًا أو مع بادئة `Bot ` اختيارية عند استخدام توكن بوت متوافق.

يستخدم البوت `discord.AllowedMentions.none()` لكل ما يرسله، لذلك لا يؤدي النص إلى تنبيه أشخاص أو أدوار أو `@everyone`.

## تثبيت التبعيات

تُثبّت كل مجموعة متطلبات في بيئة افتراضية مستقلة لتجنب تعارض تبعيات البوتين. سكربت `run_bots.sh` ينشئ البيئات الافتراضية ويثبت أو يحدّث المكتبات تلقائيًا عندما يتغير ملف المتطلبات الخاص بكل بوت، لذلك لا تحتاج إلى تعديل السكربت عند إضافة مكتبة جديدة. ملفات المتطلبات تحمل امتداد `.lock` حتى لا تلتقطها لوحات الاستضافة وتثبتها في Python العام. للتثبيت اليدوي من جذر المستودع:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r cosmo_requirements.lock

python3 -m venv second_bot/.venv
second_bot/.venv/bin/python -m pip install --upgrade pip
second_bot/.venv/bin/python -m pip install -r second_bot/cosmo_second_requirements.lock
```

يعمل مسار OCR المستخدم حاليًا للنوع الثاني باستخدام Pillow فقط، ولا يحتاج إلى OpenCV أو NumPy. أما `type1 local OCR` الجديد فهو تجربة منفصلة لبنية CNN-BiLSTM مع CTC، ولا يستورده البوت أثناء التشغيل ولا يغيّر سلوك النوع الثاني.

قبل التشغيل، أنشئ أيضًا ملف `.env` الخاص ببوت Cosmo-Coins في جذر المستودع وفق إعداداته الحالية، إن لم يكن موجودًا بالفعل. لا تستبدل ملف `.env` قائمًا.

## تشغيل البوتين معًا

من جذر المستودع:

```bash
chmod +x run_bots.sh
./run_bots.sh
```

يشغّل السكربت `main.py` الخاص بـ Cosmo-Coins من جذر المستودع، ثم يشغّل `second_bot/main.py` من مجلد `second_bot/`؛ وبذلك يقرأ كل بوت ملف `.env` الخاص بمجلده وبيئته الافتراضية. إذا لم توجد بيئة افتراضية لأحدهما، يستخدم السكربت `python3` المتاح. أوقف البوتين معًا باستخدام `Ctrl+C`.

يمكن تشغيل البوت الثاني وحده للاختبار:

```bash
cd second_bot
.venv/bin/python main.py
```

إذا كانت الاستضافة تسمح بتشغيل ملفات Python فقط، اجعل ملف التشغيل هو `run_bots.py` الموجود في جذر المستودع. هذا الملف يشغّل `run_bots.sh` تلقائيًا من المسار الصحيح، مع إبقاء بيئة كل بوت منفصلة:

```bash
python3 run_bots.py
```

## سلوك الأمر والأخطاء

- أوامر التحكم متبادلة وليست ذاتية: البوت الأساسي يستقبل `!start` و`!restart` و`!shutdown` و`!status` للتحكم في `second_bot`، والبوت الثاني يستقبل `$start` و`$restart` و`$shutdown` و`$status` للتحكم في البوت الأساسي. الأوامر محمية بمالك البوت، ويسمح البوت الثاني أيضًا بالحساب الحالي أو الرتبة الموجودة في `SAY_ALLOWED_ROLE_ID`.
- يحتفظ `run_bots.sh` بملف PID مستقل لكل بوت وملف طلبات مشترك. لذلك لا يؤدي `shutdown` لأحدهما إلى إيقاف الآخر، ولا يشغّل `start` نسخة ثانية إذا كان البوت يعمل. أمر `restart` يوقف العملية ثم يعيد تشغيل `main.py` الحالي باستخدام البيئة الافتراضية نفسها.
- بعد تنفيذ `!shutdown` استخدم `$status` من البوت الثاني للتحقق من حالة البوت الأساسي، وبعد تنفيذ `$shutdown` استخدم `!status` من البوت الأساسي للتحقق من حالة البوت الثاني. ستظهر الحالة `running (PID ...)` أو `stopped`. ويمكن كذلك فحصها من Console عبر `bash run_bots.sh control status primary` أو `bash run_bots.sh control status second_bot`.
- `$say hi` ينتظر ثانية واحدة، ثم يحذف رسالة الأمر ويرسل `hi` دون تفعيل المنشنات.
- `$ping` ينتظر ثانية واحدة ثم يعرض أن البوت متصل وزمن استجابة Gateway الحالي بالميلي ثانية.
- `$numbers` يحتاج إلى صورة مرفقة مع الرسالة، ثم يحدد نوعها محليًا. النوع الأول يمر أولًا عبر مكتبة NumPy/`struct` المحلية وقوالب `models/type1_templates.npz`، ثم يستخدم OCR.Space Engine 3 عبر أربع نسخ ومزوّدي الاحتياط عند الحاجة. أما النوع الثاني فيستخدم مسار Pillow المحلي دون أي استدعاء لمكتبة Type1 أو مزود خارجي. الصور المدعومة هي JPEG وPNG وWebP وGIF، والحد الأقصى 8 ميغابايت.
- `$testall` (للمالك أو الرتبة المصرح بها فقط) يقرأ الصور المعلّمة من `samples/label.csv`، ويرسل كل صورة من `type1` إلى Engine 3 بالمعالجات الأربع، ثم يرسل ملخص الدقة وملف `testall_engine3_report.csv`. يبيّن التقرير النتائج لكل معالجة، عدد الصور المطابقة تمامًا، حالات الخطأ برقم أو رقمين أو ثلاثة أو أربعة/خمسة، الصور غير المقروءة، وفشل الخدمة منفصلًا، إضافة إلى مواضع الأرقام التي التبس فيها التعرف. يحفظ البوت checkpoint في `second_bot/.runtime/testall_engine3_checkpoint.json` بعد كل معالجة مكتملة، ويستأنف من أول معالجة غير مكتملة بعد التوقف أو 429 دون إعادة الطلبات السابقة. عند اكتمال الاختبار وإرسال التقرير يحذف checkpoint؛ لذلك يبدأ التشغيل التالي من أول صورة. إذا تغيرت الصور أو التسميات أو نسخة المعالجة يبدأ اختبارًا جديدًا بدل استخدام نتائج قديمة. قد يستهلك الاختبار حتى 680 طلبًا للمجموعة الحالية (170 صورة). السقف اليومي المحلي 400 طلب؛ إذا وصل إليه البوت، يستأنف من checkpoint بعد تجدد الحد.
- يطبق هذا البوت الثاني cooldown شخصيًا مدته 30 ثانية لكل مستخدم وفي كل سيرفر. بوت Cosmo الأساسي لا يطبق cooldown.
- يرفع البوت النوع الأول إلى OCR.Space عبر طلب multipart، باستخدام `scale=true` و`detectOrientation=true`، مع مهلة 20 ثانية لكل محاولة. جميع أوامر البوت تمر عبر محدد مشترك يضع افتراضيًا ثانيتين بين الطلبات، يحترم `Retry-After` عند توفره، ويطبق سقفًا محليًا محافظًا قدره 400 طلب في يوم UTC مع مهلة ساعة بعد 429 إذا لم يحدد المزود مدة انتظار. تحفظ حالة المعدّل في `second_bot/.runtime/ocr_space_rate_state.json` لتبقى بعد إعادة التشغيل. تشترك أوامر `$numbers` و`$testall` في هذا الحد. تحفظ حصة Veryfi الشهرية في `second_bot/.runtime/veryfi_rate_state.json`، ولا يُستدعى إلا عند تعارض OCR.Space. تذكر [وثائق OCR.Space](https://ocr.space/ocrapi) أن الخطة المجانية محدودة بـ500 طلب يوميًا لكل عنوان IP؛ السقف المحلي يترك هامشًا، لكنه لا يحسب استعمال تطبيقات أخرى على عنوان IP نفسه.
- يحتفظ `$numbers` بفصل صارم بين المسارين: مكتبة القوالب الجديدة تُستدعى فقط بعد تصنيف الصورة كـ`type1`، بينما يبقى `extract_numbers_locally` ومسار `type2` كما هما دون تعديل. إذا تعذر تحميل نموذج Type1 أو قراءة الصورة يعود المسار إلى OCR/fallbacks المعتادة بدل التأثير في Type2.
- تُقبل الأوامر فقط في السيرفرات المشتركة بين البوتين؛ تُرفض أوامر الرسائل الخاصة والسيرفرات غير المشتركة بصمت. عند تعذر قراءة حالة البوت الأساسي أو تقادمها، يتوقف تنفيذ الأوامر حتى تُستعاد الحالة الحديثة.
- يرفض النص الفارغ أو الذي يتجاوز 2000 حرف.
- تُرفض محاولة الاستخدام من شخص ليس مالك البوت ولا يحمل الرتبة المحددة.
- يتطلب حذف أمر العضو `Manage Messages`. عند نقصها تظهر رسالة واضحة ما دام للبوت إذن الإرسال.
- تُعالج أخطاء الأمر وDiscord وتسجّل في الطرفية بدل إيقاف البوت.
- أوامر `$guilds` و`$join_guild` و`$leave_guild` محمية بمالك الحساب فقط، وتعرض رسائل آمنة عند تعذر إنشاء دعوة أو قراءة دعوة أو تنفيذ الانضمام/المغادرة.

## اختبارات الوحدة

الاختبارات مكتوبة باستخدام `unittest` ولا تتصل بـDiscord ولا تحتاج رمز بوت حقيقي. بعد تثبيت متطلبات البوت الثاني، شغّلها من داخله:

```bash
cd second_bot
.venv/bin/python -m unittest discover -s tests -v
```

تغطي اختبارات الإعدادات، صلاحيات `!say`، حذف الرسالة، النص الفارغ وحد 2000 حرف، معالجة أخطاء الأمر، وتعطيل المنشنات ونتيجة `!ping`. كما تختبر أوامر إدارة السيرفرات الثلاثة، تحليل روابط الدعوة، تحقق المالك، التأكيد قبل الانضمام، الحالات الفارغة والمنتهية و429 وعدم العثور على السيرفر، دون اتصالات فعلية بـDiscord. وتتحقق من أن OCR.Space Engine 3 وحده يُستدعى، ومن محدد الطلبات والمهلة بعد 429، وحفظ checkpoint والاستئناف من نفس المعالجة ثم بدء اختبار جديد بعد الاكتمال، دون اتصالات فعلية بـOCR.Space. وتختبر أيضًا أقنعة type1، التقسيم غير المتساوي، حالات الصور الفارغة والضوضاء، وسلوك الامتناع الآمن.

## تجربة BLUE المحلية لـtype1

توجد تجربة `evaluate_type1_rgb.py` منفصلة لاختبار إسقاطات RGB، ومنها قناة BLUE، باستخدام Pillow ومكتبات Python القياسية فقط. لا تغيّر التجربة سلوك `$numbers` ولا تفعّل نتيجة تلقائيًا. تبني القوالب من قسم التدريب فقط، وتستخدم validation منفصلًا مع تقرير يوضح نوع التقسيم وحدوده:

```bash
PYTHONPATH=second_bot python3 second_bot/evaluate_type1_rgb.py \
  --data samples \
  --variants blue \
  --max-candidates 6 \
  --report type1_blue_report.json
```

إذا لم تتوفر `batch_id`، يكون التقسيم عشوائيًا ثابتًا وليس اختبارًا مستقلًا حسب دفعات الجمع. لا تُضاف تبعيات خاصة بالتجربة؛ Pillow موجودة ضمن قفل متطلبات المشروع.

## مكتبة OCR المحلية المستقلة لـType1

أعيد تنظيم OCR المحلي للنوع الأول في `type1_ocr/` بواجهة Python قابلة للاختبار وإعادة الاستخدام. تعتمد المكتبة على Pillow وNumPy لتسريع استخراج ميزات البكسلات وإسقاطات الصفوف والأعمدة، مع مسار احتياطي يعمل دون NumPy، وتدعم PNG وWebP. تفصل التحميل والمعالجة الأولية والتقطيع والسمات والقوالب والثقة. لا تحتوي المكتبة على OCR.Space أو Gemini؛ تظل مزودات OCR الاحتياطية ضمن `main.py`. بقيت الملفات `type1_local_ocr.py` و`train_type1_local_ocr.py` و`evaluate_type1_rgb.py` كواجهات توافق لأن البوت والاختبارات والوثائق الحالية تستوردها.

اقرأ مجموعة البيانات أو درّب مرشحًا محليًا بأوامر مستقلة:

```bash
python3 second_bot/tools/inspect_type1_dataset.py --data samples
python3 second_bot/tools/train_type1.py --data samples
python3 second_bot/tools/evaluate_type1.py --data samples
python3 second_bot/tools/evaluate_type1_rgb.py --data samples --variants blue --max-candidates 6
```

يقبل قارئ البيانات صفوف `type1` فقط (309 عينة في البيانات الحالية)، ويستبعد صفوف `type2`، ولا يكتب التدريب إلى `models/type1_local_ocr.json` المستخدم اختياريًا في البوت. يوضع المرشح افتراضيًا في `models/candidates/type1_local_ocr_candidate.json` ويظل `production_enabled: false`؛ لا توجد آلية ترقية أو تفعيل تلقائي. التقسيم العشوائي لصورة داخل المجموعة لا يثبت التكافؤ مع OCR.Space/Gemini أو التعميم على دفعة مستقلة، لذا يجب إبقاء مسار البوت الحالي كما هو حتى ينجح تقييم مستقل موثق. واجهة `safe_consensus` ترفض النتائج المنفردة أو منخفضة الثقة أو المتعارضة كي يستطيع التطبيق مواصلة fallback القائم.

في تقييم seed `41` الحالي دُرّبت القوالب على 247 صورة واختُبرت على 62 صورة من تقسيم عشوائي بلا `batch_id`: كانت دقة التسلسل الكامل `0/62`، ودقة المحارف `23.87%`، مع 4 حالات امتناع. هذا أقل من خط الأساس التاريخي المذكور أعلاه (`27.5%` على 170 صورة)، مع اختلاف التقسيم والحجم فلا تُعد مقارنة مباشرة؛ لكنه لا يثبت تحسنًا، ولذلك تبقى بوابة التفعيل مغلقة.

## تنظيف الملفات غير المستخدمة

لا يمكن تحديد أن ملف Python غير مستخدم بشكل موثوق من خلال الاسم فقط، خصوصًا لأن `cogs/` تُحمّل ديناميكيًا. لذلك يوجد `cleanup_unused_files.py` في جذر المشروع بوضع معاينة افتراضي، ولا يلمس قواعد البيانات أو ملفات `.env` أو `.runtime` أو النسخ الاحتياطية أو البيئات الافتراضية أو المكتبات المثبتة داخلها.

توجد أيضًا أداة تدقيق محدودة بـ`second_bot/`؛ تعرض مراجع ملفات التوافق ولا تحذف أي مصدر أو نموذج أو صورة أو اختبار. في حال استخدام `--apply` تحفظ التقرير المحدد أولًا، ثم تزيل فقط `__pycache__` وملفات `.pyc`/`.pyo`:

```bash
python3 second_bot/tools/cleanup_unused.py --report /tmp/second-bot-cleanup.json
python3 second_bot/tools/cleanup_unused.py --apply --report /tmp/second-bot-cleanup.json
```

اعرض المخلفات القابلة للحذف والملفات المصدر التي تبدو غير مرتبطة دون حذف أي شيء:

```bash
python3 cleanup_unused_files.py --include-source
```

بعد مراجعة الناتج، احذف فقط المخلفات المولدة الواضحة مثل `__pycache__` وملفات `.pyc`:

```bash
python3 cleanup_unused_files.py --apply
```

الأداة ترفض حذف ملفات المصدر تلقائيًا؛ يجب مراجعة أي ملف مصدر يدويًا أولًا، لأن التحليل الساكن لا يستطيع اكتشاف كل الاستدعاءات الديناميكية أو الملفات المطلوبة من إعدادات الاستضافة.

يمكن فحص المكتبات المثبتة في Python العام لحساب المستخدم دون حذفها:

```bash
python3 cleanup_unused_files.py --clean-user-site
```

وعند التأكد من وجود `.venv` في جذر المشروع و`second_bot/.venv`، يمكن حذف مكتبات المستخدم فقط باستخدام `--apply --clean-user-site`. لا تلمس الأداة أبدًا مكتبات النظام في `/usr/lib` أو `/usr/local/lib`، لأن حذفها قد يعطل لوحة الاستضافة نفسها.

إذا كانت الحزم القديمة ثُبّتت باستخدام `pip` العام وليس `pip install --user`، استخدم المعاينة التالية من Python العام:

```bash
python3 cleanup_unused_files.py --clean-global-site
```

ولحذف حزم pip العامة التي يعرضها Python الأساسي بعد مراجعة القائمة:

```bash
python3 cleanup_unused_files.py --apply --clean-global-site
```

هذا الخيار لا يعمل من داخل `.venv`، ويتطلب وجود بيئتي المشروع أولًا. وهو يحذف حزم pip فقط عبر `pip uninstall`، وليس ملفات النظام أو Python نفسه. لا تستخدمه إذا كانت لوحة الاستضافة أو خدمة أخرى تعتمد على حزم pip العامة نفسها.

عند تشغيل الملف بدون أي معاملات، يعمل الآن الوضع التلقائي المكافئ لـ `--apply --clean-global-site`؛ أي أنه يحذف حزم pip العامة مباشرة بعد التأكد من وجود البيئتين الافتراضيتين. استخدم `--clean-global-site` وحده إذا أردت المعاينة فقط.
